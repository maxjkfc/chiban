## Problem Statement

想控制飲食的人，多半有一個人記錄的工具，但沒有人在看。個人飲食日誌在前三天有效，之後因為「記了也沒人知道」而中斷；而現有 App 又把記錄成本堆得很高——每一餐要選食物、填份量、對熱量，記一餐要一分鐘以上。

使用者真正的痛點不是「不知道自己吃了什麼」，而是：

- 沒有動機在吃飯當下花時間記錄。
- 記錄之後沒有任何回饋，記錄行為得不到增強。
- 想跟朋友一起飲控，但飲食內容散在各自的 App，只能靠手動轉貼到聊天群，貼完就沉在對話流裡，之後找不回來。

## Solution

吃伴讓一群朋友把「記錄飲食」與「群組聊天」合成同一個動作：拍照 → 發布，飲食紀錄即時出現在私人群組裡，朋友可以 Reaction、Reply、丟 GIF 或自訂貼圖。

關鍵在於資料模型而非畫面：`MealRecord` 是 primary data，永遠留在使用者自己的 Today / 歷史；聊天室裡的 meal message 只是它的一個 reference。因此使用者同時得到「社交回饋」與「屬於自己的飲食紀錄」，而不必在兩個 App 之間手動同步。

V0.1 不算熱量。要驗證的是：社交回饋是否足以支撐持續記錄。

## User Stories

### 帳號與 Onboarding

1. 作為新使用者，我想用 email + 密碼註冊，這樣不必等待第三方登入串接就能開始使用。
2. 作為註冊使用者，我想登入後保持登入狀態，這樣每天記錄飲食時不用重複輸入密碼。
3. 作為使用者，我想登出，這樣在共用裝置上不會讓別人看到我的紀錄。
4. 作為使用者，我想知道自己目前是誰（目前登入身分），這樣前端能正確顯示我的內容。
5. 作為使用者，我希望密碼永遠不以明文保存，這樣資料庫外洩時我的密碼不會直接曝光。
6. 作為使用者，我希望 session cookie 帶有 HttpOnly / SameSite 保護，這樣不容易被腳本竊取。
7. 作為新使用者，我想在註冊後設定暱稱，這樣朋友在群組裡認得出我。
8. 作為新使用者，我想跳過頭像設定，這樣不會在第一次使用就被卡住。
9. 作為使用者，我想設定自己的 timezone，這樣「今天」的分界符合我實際生活的時區。
10. 作為使用者，我想之後隨時修改暱稱、頭像與 timezone，這樣出國或改名時紀錄仍正確。
11. 作為未登入者，我在打開受保護頁面時應被導向登入，這樣不會看到空白或錯誤畫面。

### 群組與邀請

12. 作為使用者，我想建立群組，這樣可以找特定幾個朋友一起記錄。
13. 作為群組 owner，我想產生邀請連結或邀請碼，這樣可以用任何通訊軟體邀朋友。
14. 作為群組 owner，我希望邀請預設 7 天失效，這樣舊連結不會無限期有效。
15. 作為群組 owner，我想撤銷邀請，這樣連結外流時可以立即止血。
16. 作為群組 owner，我希望同一份邀請可以給多人使用，這樣不必一個人發一次。
17. 作為已登入使用者，我點開邀請連結應直接加入群組，這樣不必額外操作。
18. 作為未登入者，我點開邀請連結後完成註冊，應自動回到原本的邀請流程並加入群組，這樣不會註冊完就迷路。
19. 作為使用者，我想看到自己加入的所有群組，這樣可以在群組之間切換。
20. 作為群組成員，我想看到群組成員名單，這樣知道自己的飲食紀錄會被誰看到。
21. 作為使用者，我想加入多個群組，這樣家人群和健身群可以分開。
22. 作為群組成員，我希望非成員無法讀取群組內容，這樣私人群組是真的私密。
23. 作為群組 owner，我不應在未轉移 ownership 的情況下離開群組，這樣群組不會變成無人管理的狀態。
24. 作為使用者，我使用失效或已撤銷的邀請時應看到清楚的錯誤訊息，這樣知道要去要一份新的連結。

### 記錄飲食

25. 作為使用者，我想用「拍照 → 發布」兩步完成記錄，這樣在餐桌上不會拖到吃飯。
26. 作為使用者，我想一筆記錄放 1～4 張照片，這樣一桌菜或多道餐點能記在同一筆。
27. 作為使用者，我希望用餐時間預設為現在，這樣多數情況不必調整。
28. 作為使用者，我想修改用餐時間，這樣可以補記漏掉的餐。
29. 作為使用者，我想選填餐別（早／午／晚／點心／其他），這樣歷史紀錄更好讀。
30. 作為使用者，我想選填文字備註，這樣可以寫下「今天外食」之類的上下文。
31. 作為使用者，我想在發布時選擇要分享到哪些群組，這樣不是每一餐都要公開給所有群。
32. 作為使用者，我希望上傳失敗時不會留下半殘的紀錄，這樣不會看到沒有照片的空 Meal。
33. 作為使用者，我希望我的照片被移除 EXIF / GPS，這樣不會連家裡座標一起分享出去。
34. 作為使用者，我希望超大或非圖片的檔案被擋下並得到明確錯誤，這樣知道要換一張照片。
35. 作為使用者，我想編輯自己已建立的 Meal（時間、餐別、備註），這樣打錯字可以修正。
36. 作為使用者，我想刪除自己的 Meal，這樣誤記的紀錄可以移除。
37. 作為使用者，我不應該能編輯或刪除別人的 Meal，這樣紀錄的所有權是明確的。

### Today 與歷史

38. 作為使用者，我想在 Today 看到今天記錄了幾次與每筆的照片，這樣一眼知道今天的狀況。
39. 作為使用者，我希望 Today 依我的 timezone 判斷日期，這樣半夜 12 點後吃的宵夜歸到正確的一天。
40. 作為使用者，我想依日期回看過去的 Meal，這樣可以回顧一週的飲食。
41. 作為使用者，我希望 Today 不顯示熱量，這樣不會被還沒驗證的數字誤導。
42. 作為使用者，我希望刪除的 Meal 不再出現在我的飲食紀錄，這樣歷史是乾淨的。
43. 作為使用者，我在完全沒有紀錄時應看到引導我記錄第一餐的空狀態，這樣知道下一步做什麼。

### 聊天與即時互動

44. 作為群組成員，我想在群組聊天室發送文字訊息，這樣可以直接聊。
45. 作為群組成員，我希望別人的訊息不用重整就出現，這樣對話是即時的。
46. 作為使用者，我希望送出的訊息先寫入資料庫再廣播，這樣畫面上看到的訊息一定存在。
47. 作為使用者，我希望網路不穩時重送不會產生重複訊息，這樣不會洗版。
48. 作為使用者，我想往上捲載入更早的訊息，這樣不必一次載入整個聊天室。
49. 作為使用者，我希望載入更早訊息時順序穩定、不重複也不漏訊息，這樣對話讀得下去。
50. 作為群組成員，我想回覆特定訊息，這樣多線討論不會混在一起。
51. 作為群組成員，我想對訊息加上 ❤️ 😂 🔥 👏 👀 之類的 reaction，這樣可以零成本回應。
52. 作為使用者，我想收回自己的 reaction，這樣按錯可以取消。
53. 作為使用者，我希望同一個 reaction 對同一則訊息只算一次，這樣數字是可信的。
54. 作為使用者，我希望訊息被刪除後回覆串仍在，只是顯示 tombstone，這樣對話上下文不會整段消失。
55. 作為非成員，我不應能連上該群組的 WebSocket 或讀取訊息，這樣即時通道和 REST 有一致的權限。

### Meal 分享

56. 作為使用者，我發布 Meal 並選擇群組後，群組成員應即時看到 meal card，這樣分享是自動的而不是手動轉貼。

61. 作為群組成員，我應能看到分享進本群的 Meal 照片，這樣 meal card 是有內容的。
62. 作為非群組成員，我不應能透過任何 ID 讀到這筆 Meal 的照片，這樣分享範圍是可控的。

63. 作為群組成員，我想在聊天室傳送圖片，這樣可以分享菜單或截圖。

68. 作為使用者，我想刪除自己的貼圖，這樣貼圖清單可以整理。
69. 作為使用者，我不應能刪除別人的貼圖，這樣貼圖的所有權是明確的。

### 安全與存取控制

70. 作為使用者，我希望所有圖片讀取都經過後端授權，這樣沒有人能靠猜路徑拿到別人的照片。
71. 作為使用者，我希望前端永遠不知道 bucket 與 object path，這樣未來換 storage 不會影響已發出的連結。
72. 作為使用者，我希望後端不接受瀏覽器傳來的任意物件路徑，這樣不存在 path traversal 讀取面。
73. 作為使用者，我希望權限一律由後端依 session 判定，不採信前端傳來的 user_id，這樣偽造請求無效。

## Implementation Decisions

### 架構

- Go modular monolith，模組邊界依 `MVP_SPEC.md` 第 24 節：`auth`、`user`、`profile`、`group`、`meal`、`chat`、`media`、`sticker`、`storage`。跨模組呼叫走各模組匯出的 service 介面，不直接碰別的模組的 repository。
- HTTP handler 只做解析、呼叫 service、序列化。授權判斷放 service 層，這樣 REST 與 WebSocket 兩條入口共用同一份規則、不會出現只有其中一邊有檢查的漏洞。
- 前端 Next.js，mobile-first，底部導航 今日／記錄／群組／我的。

### 資料模型

- 完全採用 `MVP_SPEC.md` 第 6～18 節的 schema，不加投機性欄位（特別是任何營養／熱量欄位）。
- 所有 schema 變更走 migration；`create_all` 式的自動建表不被接受。
- 真正的 invariant 用 DB constraint 表達，至少：`group_members(group_id, user_id)` unique、`meal_group_shares(meal_record_id, group_id)` unique、`message_reactions(message_id, user_id, reaction_type)` unique、`chat_messages(user_id, client_message_id)` unique。
- 時間欄位一律 `timestamptz`，DB 存 UTC；日期分組在查詢時以 `profiles.timezone` 換算，不另存 local date 欄位。

### 授權模型

單一判斷來源，四條規則：

- **群組內容**（訊息、reaction、reply、WebSocket 訂閱）：requester 必須是該 `group_id` 的 member。
- **Meal 讀取**：requester 是 owner，或存在未 revoke 的 `meal_group_shares`，且 requester 是該 group 的 member。
- **Meal 寫入 / 刪除 / 分享**：requester 必須是 owner。
- **Avatar 讀取**：requester 是本人，或與擁有者現在同屬某個群組。`media_id` 不可猜不算檢查——id 從任何管道外流都不該可用，離開群組後伺服器端立刻拒絕。

已知界線：授權是每次請求重新判斷的，但**瀏覽器自己已抓下來的副本不受影響**。因此「立刻失效」指的是伺服器端；曾經合法看過的裝置，最多可能繼續顯示自己的快取副本到 `Cache-Control` 的存活期為止。這不會讓從未取得授權的人看到任何東西。avatar 因此只快取 60 秒，meal 照片仍為 24 小時（分享關係比群組成員資格穩定得多）。

Meal 圖片授權完全跟隨 Meal 讀取規則，不另立一套。`revoked_at` 一旦寫入即視為無效分享，讀取路徑必須實際檢查，而不是只在列表查詢過濾。

### 媒體管線

- 三種上傳（meal photo、chat media、sticker）共用同一條 media pipeline：解碼驗證 → 尺寸／大小限制 → 去除 EXIF/GPS → 交給 `ObjectStorage`。副檔名與 MIME header 不足以判定格式，必須實際解碼。
- GIF 走保留動畫的分支，不進入靜態圖 re-encode 路徑。此分支是媒體管線內的明確分岔，不是另一條管線。
- Avatar 也走這條管線，因此 avatar 上傳排在 meal photo 之後實作，不重複造輪子。
- `ObjectStorage` 是 interface（`Upload` / `Open` / `Delete`），fake-gcs 是它的一個實作；測試用 in-memory 實作。所有讀取以 application-level ID（`image_id` / `media_id` / `sticker_id`）為入口，後端自行解析 bucket 與 object name。

### 一致性

- 建立 Meal 的順序：先寫 Meal row → 上傳全部圖片 → 寫 photo metadata → 全部成功才建立 share 與 meal message。任何一步失敗，best-effort 刪除已上傳 object，並讓該 Meal 對使用者不可見。
- 不引入 queue。orphan object 由一支 maintenance script 掃描補救，接受最終一致。

### Chat 與 WebSocket

- 送訊息流程固定為：驗證 membership → 依 `(user_id, client_message_id)` upsert（命中既有列即回傳該列，不重複插入）→ 廣播已持久化的訊息。廣播的內容永遠來自 DB 回傳的 row，不是 client 送來的 payload。
- WebSocket 單向：只負責推送，不接收。送訊息一律走 `POST /groups/{id}/messages`，讓寫入只有一條路徑、一次授權檢查，「先持久化再廣播」成為結構上的必然而非兩條路徑各自遵守的約定。
- 每個 group 一個 in-process hub，單節點。不引入 Redis / Kafka。
- 分頁採 `(created_at, id)` 複合 cursor，避免同秒訊息造成漏抓或重複。cursor 對外以不透明字串呈現。
- API 對外的 `created_at` 只到秒，同秒訊息在 client 眼中無法分辨先後。因此排序責任在伺服器：client 依來源決定位置（歷史頁在前、socket 推送在後），不得依 `created_at` 重排。
- Reply 就是帶 `reply_to_message_id` 的 chat message；不建立獨立的 comment 模組。parent 在讀取時 join 出來、不在寫入時複製，所以 parent 被刪除會同時反映在每一則引用它的訊息上。
- 訊息刪除是軟刪除，且刪除後仍留在歷史裡作為 tombstone：把它從查詢中濾掉會讓底下的回覆失去上下文。content 在 store 層就清空，不依賴呼叫端記得不要外流。
- Reaction 的唯一性由 `message_reactions` 的 primary key `(message_id, user_id, reaction_type)` 保證，不由應用層先查再寫。取消 reaction 的 SQL 一律帶 `user_id`，所以沒有任何語句能刪掉別人的。
- 可用的 reaction emoji 是產品決定，放在應用層並由 `GET /reaction-types` 對外，避免前後端各自維護一份而漂移。
- WebSocket 推送使用單一信封 `{type, ...}`，目前有 `message`、`reaction`、`deleted` 三種。刪除只送 message id：訊息帶有 per-reader 的 reaction 狀態，一次廣播不可能對每個人都正確。
- Meal 分享產生的 chat message 只帶 `meal_record_id`，不複製 description 或任何圖片路徑。meal card 的內容由 client 依 `meal_record_id` 打 `GET /meals/{id}` 取回，不由 API 在讀取時 join：卡片因此永遠跟著 Meal 自己的授權走，取消分享或刪除當下就失效，而不需要另一套判斷。
- 一個 Meal 在一個群組只有一張卡，由 `chat_messages` 上的 partial unique index `(group_id, meal_record_id) WHERE meal_record_id IS NOT NULL AND deleted_at IS NULL` 保證，不由應用層先查再寫。取消分享後再分享會重新開啟存取、但不會再開一段對話。
- Meal 的 `eaten_at_local` 一律以**擁有者**的 timezone 換算，不是讀取者的。它描述的是擁有者那一天的事實：在台北 12:30 吃的午餐，對每個看得到它的人都是 12:30。
- 分享的寫入順序是先寫 `meal_group_shares` 再公告：卡片先到會指向一個當下還沒有人能打開的 Meal。
- `meal` 模組不讀 `group_members`。它定義 `Membership`（回傳 reader 所屬的 group id）與 `Announcer`（把卡片貼進群組）兩個 consumer-defined interface，分別由 `group` 與 `chat` 滿足，在 `httpapi` 組裝。代價是每次讀 Meal 或 Meal 圖片多一次成員查詢。

### API 契約

沿用 `MVP_SPEC.md` 第 28 節的端點清單。實作時可微調命名，但下列語意不可變更：媒體一律以 application ID 讀取、meal 分享是獨立資源、reaction 以 `reaction_type` 為刪除鍵、聊天分頁用 `before` cursor。

## Testing Decisions

### 什麼算好測試

只測外部可觀察行為：HTTP 狀態碼與 response body、WebSocket 收到的訊息、DB 中可查得的結果。不測私有函式、不斷言呼叫次數、不 mock 自己家的 service。測試名稱描述行為與理由（「非成員讀取群組訊息回 403」），不是描述函式名。

每個測試必須能因 business logic 改變而失敗——新增測試時先讓它紅過一次，再讓它綠。

### 主 seam：HTTP + WebSocket

整個 V0.1 只有一個主要測試 seam：對真實 PostgreSQL 啟動完整 API server，測試透過 `/api/v1` 與 WebSocket 進出。理由是授權是本專案風險最高的部分，而授權只有在完整 middleware + handler + service 串起來時才是真的；service 層測試會漏掉 middleware 的缺口。

- DB：真實 PostgreSQL（docker compose 或 testcontainers），每個 test case 跑在會 rollback 的 transaction 或獨立 schema 上。不用 sqlite、不用 mock DB。
- Storage：in-memory 的 `ObjectStorage` 實作。真實 fake-gcs 只在 infra slice 有一個 smoke test 證明介面接得上。
- Fixtures：一組 helper 負責「建立已登入使用者」「建立群組與成員」「建立含照片的 Meal」，讓每個測試的前置條件是一行。這組 helper 是 slice 0 的交付物之一。

### 例外：純函式 unit test

只有以下三類邏輯值得獨立 unit test，因為它們是純輸入輸出、且邊界條件多到不適合用 HTTP 測試枚舉：

- timezone 日界計算（跨日、跨時區、DST）。
- 圖片 sanitize 判定（格式偵測、尺寸／大小上限、EXIF 移除、GIF 動畫保留）。
- cursor 編解碼與排序穩定性。

除此之外不新增 seam。

### 必須被測到的行為

每個 slice 至少涵蓋自己範圍內的授權負向案例。整個 V0.1 收斂時，下列必須有測試：session 驗證、群組成員資格與邀請有效性、Meal 所有權、分享與撤銷分享後的 Meal／圖片可讀性、媒體授權、timezone 日期分組、WebSocket 授權、persist-before-broadcast、`client_message_id` 重送冪等、reply／reaction 完整性、上傳失敗清理。

### 前端

前端不設獨立測試層。V0.1 的前端驗收方式是 `MVP_SPEC.md` 第 31 節的 end-to-end 手動走查，在最後一個 slice 執行並記錄結果。

### 建議里程碑

| 里程碑 | 涵蓋 slice | 意義 |
|---|---|---|
| M1 可登入的空殼 | 0–2 | 環境與測試 seam 就位，身分可用 |

M3 是最重要的判斷點：核心 loop 一通就該找朋友實際用幾天，再決定 slice 10–12 的優先序。

## Out of Scope

`MVP_SPEC.md` 第 32 節的整份清單全部排除，本文件不重述。額外在本輪明確排除的實作面決定：

- 前端自動化測試（元件測試、Playwright e2e）。V0.1 靠手動走查驗收。
- 多節點 WebSocket、presence、typing indicator、read receipt。
- Signed URL、CDN、image CDN 變體尺寸。
- 從他人訊息收藏貼圖、貼圖包、GIF 搜尋供應商。
- 通知（push / email / in-app badge）。
- 帳號刪除、資料匯出、密碼重設信。V0.1 使用者是可直接聯絡的小圈子，這些延後。
- Rate limiting 與 abuse 防護，除了檔案大小／尺寸上限這種必要的輸入驗證。
- i18n。V0.1 只有繁體中文介面。

## Further Notes

- **最大的實作風險是授權**：Meal 分享是一個會被撤銷的關係，因此每一條讀取路徑都必須實際檢查 `meal_group_shares`，包括圖片串流。設計 slice 9 時要先寫「取消分享後成員讀不到圖片」的紅測。
- **第二大風險是 storage 與 DB 的不一致**：slice 4 是唯一同時碰兩個系統的地方，之後的 media slice 都復用它的清理路徑，因此在 slice 4 就要把失敗清理做對，不要留到之後補。
- **timezone 只有一處**：所有日期分組都必須通過同一個純函式，不允許各查詢自行 `AT TIME ZONE`。這是 slice 5 的設計約束。
- **不要為 V0.2 預留欄位**。roadmap 上的營養模型會在有真實資料之後才定型，現在預留只會綁死。
- 本文件描述行為與決策，不含檔案路徑與程式碼片段；實作細節以程式碼與 migration 為準。
